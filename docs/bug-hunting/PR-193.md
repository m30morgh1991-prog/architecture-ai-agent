# Bug Hunt Evidence — PR 193 Architectural Client Brief & Requirements Analysis

## Scope

Documentation-only change defining the architectural requirements workflow: Client Intake, Architectural Analysis, Designer Brief, and Approved Architectural Design Brief. It separates client-facing intake from professional architectural analysis and records evidence provenance, confidence, conflicts, versioning, approval, and traceability into the existing PlanModel and ConstraintMap.

No runtime code, schemas, tests, BIM/CAD editing, geometry generation, rendering, or execution behavior is changed. This PR records a product requirement; it does not claim the feature is implemented.

## Bug Hunt

Reviewed the proposed workflow for ambiguity that could accidentally turn client statements into verified architectural facts, promote uncertain requirements into executable constraints, or bypass the existing approval and validation pipeline.

The review checks that source/evidence provenance, confidence, unresolved conflicts, version history, explicit approval, and downstream traceability are described as requirements rather than assumed implementation capabilities.

## Findings

- Client-provided statements and preferences are requirements/evidence inputs, not verified geometry, code compliance, or authoritative PlanModel facts.
- Missing, contradictory, low-confidence, or unverified information must remain unresolved and require clarification or source evidence.
- The Designer Brief is an intermediate professional artifact; it is not an Approved Architectural Design Brief.
- Approval must be explicit and version-bound. A changed brief must not inherit approval from an earlier version.
- Traceability to PlanModel/ConstraintMap is a requirement only; this documentation does not create or mutate either model.
- No implementation defect is asserted or silently marked fixed by this documentation-only PR.

## Root Cause

The product requirements needed a clear boundary between collecting a client's wishes, professional architectural interpretation, communicating a designer-ready brief, and approving a version for downstream use. Without this separation, client statements could be mistaken for verified design facts or an approved change request.

This PR addresses the documentation gap only. It does not claim that a runtime requirements-intake engine, approval service, or PlanModel/ConstraintMap integration exists.

## Regression

- Preserve the existing PlanModel + ConstraintMap + ApprovedChangePlan source-of-truth architecture.
- Preserve fail-closed handling for UNKNOWN, SOURCE_REQUIRED, NEEDS_REVIEW, ABSTAIN, and BLOCKED.
- Do not promote client assertions, assumptions, or unresolved conflicts to PASS.
- Do not treat a Designer Brief as approval to edit.
- Do not transfer approval across changed brief versions.
- Do not add runtime dependencies, alter execution paths, or modify Golden DWG assets.
- Require exact-head CI evidence; stale or incomplete workflow results are not a Green Gate.

## Required fail-closed states

UNKNOWN, SOURCE_REQUIRED, NEEDS_REVIEW, ABSTAIN, and BLOCKED remain unresolved states and never become PASS without appropriate evidence. Conflicting or missing requirements remain NEEDS_REVIEW or SOURCE_REQUIRED. Client-provided assertions do not grant EDITABLE permission, authorize geometry changes, or substitute for an ApprovedChangePlan.
