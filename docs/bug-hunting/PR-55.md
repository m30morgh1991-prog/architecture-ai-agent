# H95: idempotent execution recovery

## Scope
H95 integrates the existing idempotency guard with the /v1/execute runtime boundary.

## Bug Hunt
### reproduction
Submitting the same completed execution_id to the /v1/execute runtime previously reached the execution-record duplicate path and returned DUPLICATE_EXECUTION_ID, with no deterministic recovery of the completed result.

### root cause
runtime/idempotency.py existed but was not connected to the HTTP execution boundary. The producer/consumer contract therefore had an unused guard while ExecutionRecordStore treated every repeated identifier as an error.

### regression
The guard now stores the first completed result and the runtime checks it before creating a new execution record. A completed duplicate is replayed without rerunning the operation. An in-flight or unknown duplicate remains HTTP 409 with idempotency_state=UNKNOWN, so missing evidence cannot become PASS.

### fail-closed verification
UNKNOWN, NEEDS_REVIEW, BLOCKED, missing evidence, and unresolved state are never promoted to PASS or LOCKED. The idempotency layer grants no edit authority.

## Findings
- Completed duplicate: deterministic replay.
- In-flight/unknown duplicate: fail-closed 409.
- The cached result is returned together with the existing execution record.
- No edit authority is granted by idempotency; it only prevents duplicate execution.

## Regression
Permanent coverage was added for completed replay, unknown keys, duplicate preservation, and clearing replay evidence. Runtime integration uses the same guard before execution-record creation and after final result creation.

## CI Verification
Required gates: Bug Hunt Gate, PR CI Gate, Runtime Tests, Regression. Any failing or missing gate is treated as non-green.

## Final Decision
H95 is mergeable only if the required gates are successful and post-merge main CI is observable and verified. Missing or UNKNOWN CI evidence means MERGE = NO.
