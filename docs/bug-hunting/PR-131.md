## Scope

PR #131 adds an isolated DWG-to-DXF conversion experiment for the two Golden DWG fixtures. It does not change the architectural reasoning core, source DWG files, or production editing behavior.

## Bug Hunt

The first exact-head run exposed a real adapter-contract bug before conversion: the test treated the ezdwg Layout object as directly iterable. The implementation was corrected to use the public query interface where available and to normalize ezdwg/ezdxf entity type access. The next run completed conversion but exposed default converter heuristics that changed the modelspace; those results were correctly marked NEEDS_REVIEW.

## Findings

- The dependency installation succeeded on GitHub Actions with ezdwg 0.19.2 and ezdxf 1.4.5.
- The first conversion attempt did not reach the conversion call because of the Layout iteration TypeError.
- The first completed default conversion run exposed major fidelity loss. For Afifiiiii, ezdwg reported 430 entities written while the source modelspace inventory contained 72,921 entities; Bagheri7 reported 19,262 written versus 13,208 source entities and skipped six TEXT entities. The outputs reopened, but both were marked NEEDS_REVIEW.
- Source inspection of ezdwg `convert.py` confirmed automatic modelspace-selection and geometry-cleanup heuristics. A second run with `modelspace_only=True` avoided those heuristics but wrote only two entities for each drawing. This demonstrates that ezdwg could not reliably identify the full modelspace from the ownership metadata in these fixtures.
- Supplying every observed source entity type explicitly did not improve the `modelspace_only=True` result: both fixtures still yielded only two output entities. This points to unreliable ownership/placement filtering in these inputs, not merely type discovery.
- The strict native DWG writer probe ran on both files and was BLOCKED before creating output copies. Bagheri7 failed on block XDATA, preview, extension dictionaries and Xref metadata; Afifiiiii failed on block XDATA, preview and extension dictionaries. This is the expected fail-closed behavior and confirms the native writer cannot currently round-trip these Golden files losslessly.
- Original DWGs remain read-only; before/after SHA-256 equality is a required check.
- The latest completed conversion run (#19) still reports severe fidelity loss: Afifiiiii lost 72,447 LINE entities, 8 DIMENSION, 141 HATCH, 151 INSERT, 70 LWPOLYLINE, 14 MTEXT, and 85 TEXT entities; its source hash remained unchanged. The native writer probe remained BLOCKED.
- That run also exposed a separate evidence-harness defect: `source_layer_names` was reported as only `["0"]`, while the converted file contained many named layers. The previous helper defaulted missing source entity layer attributes to `0`, making the source-vs-output layer comparison non-authoritative.
- The layer inventory now resolves modelspace entity handles through ezdwg's raw `decode_entity_styles` and `decode_layer_names` APIs. Missing entity-to-layer links are counted and fail closed instead of being silently replaced with layer `0`; focused regression tests cover valid, missing, and unknown layer handles.
- A successful DXF reopen is not proof of lossless conversion, AutoCAD visual equivalence, DWG write-back safety, architectural interpretation, or regulatory compliance.

## Reproduction

Run the `Golden DWG to DXF Fidelity Test` workflow for PR #131. It installs the DXF extra, converts each manifest Golden DWG to DXF R2010, independently reopens the result with ezdxf, compares entity counts and layer names, runs DXF audit, and uploads reports plus DXF files.

## Root Cause

There are two independent issues. First, the source and destination libraries expose different layout iteration contracts: ezdwg's Layout is queried through `query()`; ezdxf modelspace can be iterated directly. Entity type access also differs: ezdwg exposes a string-like `dxftype`, while ezdxf exposes `dxftype()`. Second, ezdwg's common entity layer assignment is represented by layer handles in its raw entity-style data and layer table; the earlier helper looked only for a `dxf.layer` value and silently substituted `0`. The layer inventory now joins modelspace entity handles to layer handles and then to layer names using the documented raw API.

## Regression

The helper normalizes layout enumeration and entity type access across both libraries. Source layer names are resolved through raw entity-style and layer-table handle mapping; unresolved handles are explicit and prevent PASS. Focused unit tests cover successful mapping, missing entity mapping, and unknown layer handles. A regression is any failure to reopen output, any source hash change, any skipped entity, entity-count delta, incomplete source layer inventory, layer delta, or DXF audit issue.

## Required fail-closed states

Any unsupported entity, changed source hash, output parse failure, count mismatch, layer mismatch, or audit issue must remain `NEEDS_REVIEW` or `BLOCKED`. Missing evidence is `UNKNOWN`. No uncertain conversion may be promoted to PASS.

## CI Verification

The Bug Hunt unit tests passed on the first PR run. The exact-head conversion workflow #19 completed conversion but failed the fidelity gate, as expected. The layer-inventory defect found in its report is being corrected with raw-handle mapping and focused regression tests. `PASS` on the general PR CI, Runtime Tests, or Bug Hunt workflows refers only to those suites, not to DXF fidelity. The merge gate must remain blocked: both DXF conversion paths are NEEDS_REVIEW and the native writer is BLOCKED for both files. The workflow is being made fail-closed at the job level, with artifact upload forced even when fidelity checks fail.

## Affected Contracts

- Golden DWG inputs are immutable evidence fixtures.
- DWG extraction and conversion are adapters only; they do not establish architectural semantic authority.
- DXF conversion fidelity report is separate from runtime validation and human visual review.
- Unit metadata is evidence only; scale and measurement interpretation remain independent checks.

## Risk Classification

High risk for any workflow that treats converted DXF as an editable source of truth. Medium risk for read-only extraction and review. This PR is an isolated test only; it does not authorize production write-back.

## Negative Tests

- A modified source file must fail the SHA-256 immutability check.
- A missing or empty DXF must fail the conversion workflow.
- An unsupported/skipped entity must produce `NEEDS_REVIEW`.
- Entity-count or layer-name differences must produce `NEEDS_REVIEW`.
- DXF audit errors or fixes must produce `NEEDS_REVIEW`.
- Missing report or exact-head evidence must block merge and prevent a false pass.

## Unresolved Findings

The explicit-type modelspace-only run completed and still wrote only two entities for each fixture, so it is rejected. The latest run #19 independently confirms large entity-count losses; source layer names from the old helper were incomplete and must not be used as fidelity evidence. The strict native writer probe completed and blocked both files before output creation due to unsupported block metadata. The conversion reports remain NEEDS_REVIEW, and the strict writer status is BLOCKED. AutoCAD 2020 visual inspection and a separate DWG write-back test are still unresolved and are not covered by this PR.

## Final Decision

BLOCKED for merge. Current evidence does not support lossless DWG-to-DXF conversion or native DWG write-back for either Golden fixture. The final workflow must fail CI on NEEDS_REVIEW/BLOCKED while still uploading reports. A green test-harness step is not a fidelity PASS.
