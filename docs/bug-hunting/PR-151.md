# Bug Hunt — idempotency request-payload binding (PR 151)

## Scope
Fix the existing idempotency defect where a completed execution result is replayed solely by execution ID, even if a later request reuses that ID with a different payload.

## Bug Hunt
The regression test exercises the real HTTP handler with an isolated in-memory execution store, audit trail, and idempotency guard. It verifies that an identical request is replayed, while a different request using the same execution ID receives HTTP 409.

## Findings
- `runtime/idempotency.py` currently indexes completed results only by key.
- `runtime/app.py::Handler.do_POST` checks the execution ID before comparing any request identity.
- A different payload using the same key can therefore receive the previous request's cached result and appear successful.
- This violates execution provenance and can bind a result to the wrong project/version/plan/request.

## Reproduction
From the repository root, run:
`python -m unittest tests.test_idempotency.IdempotencyTests.test_same_execution_id_with_different_payload_returns_conflict -v`.
The test sends an initial request, repeats it unchanged, then changes the instruction while keeping the execution ID identical.

## Root Cause
The idempotency cache stores only `execution_id -> result`; it does not retain or compare a canonical request fingerprint. The handler therefore treats key equality as proof of request equality.

## Regression
The expected behavior is: first request returns 200 and is not a replay; identical retry returns 200 with `idempotent_replay=true`; same key with a changed payload returns 409 and `IDEMPOTENCY_KEY_REUSED_WITH_DIFFERENT_REQUEST`.

## Required fail-closed states
A key reused with a different request must be a conflict, never a PASS or cached replay. UNKNOWN, NEEDS_REVIEW, and BLOCKED remain unresolved. No false pass is allowed. An identical retry may replay only when its canonical request fingerprint matches.

## CI Verification
The test is committed before the implementation so CI can demonstrate the original behavior. The test-only commit creates a new exact-head SHA; only completed/success PR CI, Runtime Tests, and Bug Hunt checks on the final exact head count as PASS. No test result is claimed until the workflow output is inspected.

## Affected Contracts
- `runtime/idempotency.py` key-to-request/result binding.
- `runtime/app.py` request fingerprint calculation and conflict response.
- `tests/test_idempotency.py` HTTP-boundary regression.
- No PlanModel, ConstraintMap, BIM semantics, CAD provider, or Golden DWG changes.

## Risk Classification
High safety significance: replaying a result for a different request can corrupt execution traceability and report an incorrect outcome. The fix remains limited to deterministic request identity and replay conflict handling.

## Negative Tests
- Same key and same canonical payload replays the original result.
- Same key and changed instruction returns HTTP 409.
- Same key and changed project/version/plan data cannot replay a different request's result.
- Different key can be processed independently.
- No conflicting payload overwrites the first stored result.
- No automatic approval, real CAD write, H-stage advancement, or merge is authorized.

## Unresolved Findings
- In-flight key reservation/atomicity for a future threaded server remains a separate concern.
- Execution and audit persistence remain in-memory and are not made durable by this change.
- HTTP schema validation, body-size limits, safe network binding, and exception handling remain separate P0 blockers.
- Windows/AutoCAD host tests remain NOT_RUN.
