# Bug Hunt Evidence — PR 172 HTTPS transport security contract

## Scope

This PR records the approved transport-security design baseline for the Architecture AI Agent. It is documentation-only and defines HTTPS/TLS expectations for operational Web App/PWA traffic, local development, and internal service communication. It does not implement TLS, authentication, remote access, or runtime changes.

## Bug Hunt

Review focused on false security claims, plaintext credential exposure, untrusted forwarded headers, TLS termination boundaries, confusion between transport encryption and authorization, accidental reopening of the legacy execution route, unsafe local-development exposure, provider lock-in, and unsupported performance claims.

## Findings

- HTTPS is mandatory for non-loopback operational client-to-service traffic.
- Plain HTTP is not an operational transport. Local HTTP is restricted to loopback development without production credentials or real user data.
- TLS termination must occur at an explicit configurable edge; the runtime remains private.
- Forwarded headers are trusted only from explicitly configured proxies.
- Authentication and authorization remain separate mandatory controls; HTTPS alone does not authorize requests.
- CSRF/origin policy depends on the selected authentication mechanism; CORS must use an explicit origin allowlist.
- TLS baseline, certificate validation/renewal, secret redaction, request bounds, and abuse controls are recorded as acceptance requirements.
- HTTP/2 and HTTP/3 are optional performance candidates requiring benchmarks; HTTPS is not claimed to increase throughput by itself.
- The canonical execution chain remains the only edit authority. Client-supplied geometry, EDITABLE states, approvals, or snapshots cannot authorize changes.
- PR #171 remains interim fail-closed containment. This document does not enable remote access or reopen the legacy endpoint.
- Hosting, reverse-proxy, certificate, identity, and AI providers remain replaceable; no vendor dependency is introduced.

## Reproduction

Review docs/architecture/https-transport-security-contract.md and verify:
1. The operational HTTPS requirement and loopback-only local development exception are explicit.
2. TLS termination, private runtime, and trusted-proxy rules are explicit.
3. Authentication/authorization, CSRF/origin, CORS, certificate, logging, and abuse controls are distinguished from TLS.
4. The canonical execution chain is retained and client-provided state cannot grant edit authority.
5. PR #171 is explicitly preserved as fail-closed and no remote execution is enabled.
6. HTTP/2/HTTP/3 are treated as benchmarked optional optimizations, not guaranteed speed improvements.
7. No runtime file, executable rule, CAD write path, or model semantics are changed.

## Root Cause

The runtime security work identified that remote access must remain disabled until authentication and TLS are designed and reviewed. Without a durable transport contract, future implementation could expose plaintext HTTP, trust spoofed proxy headers, mistake HTTPS for authorization, or bind deployment assumptions to a particular vendor.

## Regression

- Operational non-loopback traffic requires HTTPS with a valid trusted certificate.
- Local development remains loopback-only and cannot become a LAN/public deployment through an implicit default.
- TLS does not substitute for identity, authorization, CSRF/origin controls, or canonical execution authority.
- Untrusted forwarded headers cannot alter security decisions.
- No secrets may be placed in URLs or unredacted logs.
- Remote mutation routes remain closed until all acceptance controls are implemented and reviewed.
- Performance changes require measurement and cannot weaken security.
- Documentation-only changes do not alter runtime or CAD behavior.

## Required fail-closed states

- UNKNOWN: deployment trust boundary, proxy identity, certificate state, or request authority is uncertain.
- SOURCE_REQUIRED: deployment-specific certificate, identity, or proxy configuration evidence is missing.
- NEEDS_REVIEW: security policy, origin, CSRF, or deployment exception requires human review.
- BLOCKED: plaintext operational access, invalid TLS, missing authentication/authorization, or missing canonical authority prevents remote mutation.
- PASS: prohibited for remote execution until every required control is implemented and verified.
- No TLS success may promote an unauthorized request or uncertain architectural state to PASS.

## Risk Classification

High security significance, documentation-only implementation scope. The primary risk is treating the design document as evidence that HTTPS or authentication is already deployed. The PR explicitly states that no runtime effect or remote access is enabled until a separate implementation and verification phase.

## Negative Tests

- A public/LAN HTTP endpoint cannot accept credentials or execute mutations.
- Invalid, expired, hostname-mismatched, or untrusted certificates cannot be bypassed.
- Client-supplied forwarding headers cannot spoof the trusted proxy or transport scheme.
- HTTPS alone cannot authorize a request.
- Missing authentication/authorization or CSRF/origin protection blocks remote mutation.
- Secrets are not accepted in query strings or written unredacted to logs.
- The legacy execution route remains BLOCKED until canonical server-owned evidence and the full approval/impact chain exist.
- No client-supplied EDITABLE, geometry, approval, or detached snapshot bypasses canonical authority.
- HTTP/2/HTTP/3 are not assumed faster without representative benchmarks.
- Local development defaults cannot bind to 0.0.0.0 or an untrusted interface.
- No runtime, geometry, BIM, CAD, or Golden DWG behavior is changed by this documentation PR.

## Unresolved Findings

- Implement and test the TLS edge/runtime boundary for the selected deployment profile.
- Implement authentication, authorization, session/token lifecycle, CSRF/origin controls, and explicit CORS allowlisting.
- Implement trusted-proxy configuration and forwarded-header sanitization.
- Implement certificate issuance, validation, renewal, expiry monitoring, and rotation.
- Add request/read timeouts, rate limits, bounded concurrency, and security audit coverage.
- Reconcile the dependent PR #150 → #151 → #152 → #154 stack with PR #171 before merging any part of the stack.
- Benchmark HTTP/2/HTTP/3 only after correctness and security gates pass.
- Keep remote access and mutation routes disabled until exact-head tests and human security review pass.

## Final Decision

Design-contract documentation only. Safe to consider for human review only after fresh exact-head PR CI Gate, Runtime Tests, and Mandatory Bug Hunt all pass. This PR does not claim HTTPS implementation, does not enable remote access, and does not authorize reopening the legacy endpoint.
