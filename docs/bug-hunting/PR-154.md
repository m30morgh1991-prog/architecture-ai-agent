# Bug Hunt — HTTP request guardrails and loopback-only binding (PR 154)

## Scope
Harden the existing JSON execution endpoint against malformed/ambiguous requests, oversized bodies, and accidental network exposure. This is a security and reliability correction, not a new product feature.

## Bug Hunt
The current handler trusts Content-Length, reads the body without a maximum, assumes valid JSON and required fields, and allows the runtime to bind to all network interfaces without authentication or TLS.

## Findings
- Missing or non-numeric Content-Length can raise exceptions.
- Oversized bodies are read without a cap.
- Wrong Content-Type and malformed JSON are not rejected through structured responses.
- Non-object JSON and missing/wrongly typed fields can raise KeyError/TypeError during execution.
- Unknown element editability states can raise ValueError in the controlled-editing contract.
- The server currently binds to `0.0.0.0:8000`, exposing an unauthenticated, non-TLS endpoint to the network.

## Reproduction
Run:
`python -m unittest tests.test_http_request_guardrails -v`.
The tests exercise Handler.do_POST using bounded fake streams and verify malformed, missing, oversized, wrong-content-type and invalid-schema requests receive structured 4xx responses without execution. A separate test asserts the default runtime binds only to loopback.

## Root Cause
The HTTP boundary does not validate transport metadata or the request schema before accessing request fields and invoking the runtime. The server's default bind address is wider than the current unauthenticated API can safely support.

## Regression
The tests require:
- missing Content-Length → 411;
- invalid Content-Length → 400;
- body larger than the configured limit → 413 before reading;
- non-JSON Content-Type → 415;
- malformed JSON, non-object JSON, missing fields and invalid element state → 400;
- default server bind → 127.0.0.1 only.

## Required fail-closed states
Malformed, incomplete, unsupported or oversized requests are rejected before execution. No execution record, idempotency cache entry, approval, or PASS audit event may be created for a rejected transport/schema request. Remote binding remains disabled until authentication and TLS are implemented and reviewed.

## Affected Contracts
- `runtime/app.py` HTTP transport validation and default bind address.
- `tests/test_http_request_guardrails.py` request-boundary and loopback regression coverage.
- No PlanModel, ConstraintMap, BIM, CAD conversion, or Golden DWG changes.

## Risk Classification
High security significance. The API currently has no authentication or TLS. Loopback-only binding is the safe default until a reviewed remote-access design exists. The body cap is applied before reading untrusted payload bytes.

## Negative Tests
- Missing Content-Length does not reach JSON parsing.
- Invalid/negative/non-digit Content-Length does not reach body reading.
- Oversized body is rejected without reading.
- Unsupported content type is rejected before parsing.
- Malformed JSON and duplicate/invalid structure do not reach execution.
- Unknown state cannot be interpreted as editable.
- Remote interface binding is not enabled by default.
- No arbitrary JSON or Python objects are silently coerced to strings.

## Unresolved Findings
- Authentication, TLS, CSRF/origin controls and explicit remote deployment configuration are not implemented; network access remains disabled by default.
- Persistent execution, audit and idempotency records remain in-memory.
- Request rate limits and concurrent in-flight idempotency reservations remain future hardening requirements.
- Canonical PlanModel/ConstraintMap pipeline integration and real CAD writer remain separate blockers.
