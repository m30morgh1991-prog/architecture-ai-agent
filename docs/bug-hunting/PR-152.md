# Bug Hunt — successful HTTP response serialization (PR 152)

## Scope
Fix the existing HTTP response defect where successful runtime execution results contain nested dataclass values that the legacy handler's plain `json.dumps` cannot serialize.

## Bug Hunt
The regression test calls the real `Handler._json` method with the same nested response shape returned by a successful execution: an ApprovedChangePlan dictionary containing a ChangeRequest dataclass.

## Findings
- `runtime/app.py::execute` returns an ApprovedChangePlan representation whose `request` member is a ChangeRequest dataclass.
- `Handler.do_POST` places this value in the response body.
- `Handler._json` calls plain `json.dumps(body)`, which raises TypeError for the nested dataclass.
- This means a successful simulated execution can complete internally but fail while writing its HTTP response.

## Reproduction
From the repository root, run:
`python -m unittest tests.test_http_response_serialization.HttpResponseSerializationTests.test_json_response_serializes_nested_change_request_dataclass -v`.
The test passes the nested ApprovedChangePlan response shape to Handler._json and verifies the resulting JSON structure.

## Root Cause
The HTTP serializer assumes every nested response value is natively JSON-serializable. It does not convert dataclass instances such as ChangeRequest to JSON-compatible mappings.

## Regression
The test requires Handler._json to serialize the nested ChangeRequest, return valid JSON, and preserve the instruction and approved target IDs. It is committed before the production fix.

## Required fail-closed states
Serialization failure must never be misreported as a successful HTTP response. UNKNOWN, NEEDS_REVIEW, and BLOCKED remain unresolved. No false pass, real CAD write, or approval authority is introduced.

## CI Verification
This test-only commit creates a new exact-head SHA. PR CI Gate, Runtime Tests, and Bug Hunt must complete/success on the final exact head. The expected RED result is a test assertion failure identifying the TypeError from plain json.dumps; no green result is claimed until the workflow output is inspected.

## Affected Contracts
- `runtime/app.py::Handler._json` response serialization only.
- `tests/test_http_response_serialization.py` regression coverage.
- No PlanModel, ConstraintMap, BIM, CAD provider, or Golden DWG changes.

## Risk Classification
High runtime significance because the HTTP API may drop the response after a successful simulated execution. The fix should only convert known dataclass values to JSON-compatible structures and must not silently stringify arbitrary unsupported objects.

## Negative Tests
- Nested ChangeRequest dataclass serializes to an object with its declared fields.
- Approved target IDs remain a JSON array.
- Existing primitive/dict/list responses remain unchanged.
- Unsupported arbitrary objects continue to raise a serialization error rather than being silently stringified.
- No automatic approval, real CAD write, H-stage advancement, or merge is authorized.

## Unresolved Findings
- The legacy runtime remains a simulation and is not wired to the canonical PlanModel/ConstraintMap pipeline.
- HTTP request schema validation, body-size limits, safe network binding, exception-to-response handling, and persistent execution/audit state remain separate P0 blockers.
- Windows/AutoCAD host tests remain NOT_RUN.
