## Scope

POL-02: prevent a boolean `authorized=True` flag from bypassing a LOCKED element permission in the controlled-editing contract. The change is limited to the permission contract, its regression tests, and this evidence record.

## Bug Hunt

Source inspection found that `EditPermission.validate()` accepted `LOCKED` with `authorized=True`, and `ControlledEditingDecision.blocking_reasons()` then omitted the locked-element conflict. This made a bare boolean sufficient to turn a protected element into an executable decision at the contract boundary.

The real-visual bridge separately checks that approved targets are EDITABLE in the PlanModel before calling execution. That downstream defense remains in place, but it does not make the standalone contract safe for other callers.

## Findings

POL-02: a bare authorization boolean could suppress the LOCKED_ELEMENT_CONFLICT in the controlled-editing contract without an approval record bound to the specific proposal, project, source version, and target set. For the MVP's protected-element policy, LOCKED remains non-editable; an authorization flag cannot unlock it.

## Reproduction

Test-first regression added for `EditPermission("W01", "LOCKED", authorized=True)`. On the pre-fix source snapshot, the new test failed because no `ValueError` was raised (1 failing test).

After the fix, the following focused local tests passed:
- `tests/test_controlled_editing_contract.py`
- `tests/test_h48_end_to_end_approval_bridge.py`
- `tests/test_controlled_editing_e2e_gate.py`

Combined pytest result: 18 passed. This is targeted validation, not a full repository test-suite result.

## Root Cause

The contract treated the `authorized` boolean as sufficient authority for a LOCKED element. It was not cryptographically or structurally bound to an approval record, proposal, source version, or target set. The decision's blocking logic also trusted that boolean and removed the locked-element blocker.

## Regression

The contract now rejects `authorized=True` for LOCKED permissions with `EDIT_PERMISSION_LOCKED_AUTHORIZATION_UNSUPPORTED`. Independently, `blocking_reasons()` always reports `LOCKED_ELEMENT_CONFLICT:<element_id>` for LOCKED permissions, even if a caller constructs the decision directly and skips validation.

Editable and conditional permission behavior remains unchanged. The real-visual bridge and post-edit validation were not modified.

## Required fail-closed states

LOCKED remains blocked. A boolean authorization flag cannot convert LOCKED to EDITABLE or suppress a conflict. UNKNOWN, SOURCE_REQUIRED, NEEDS_REVIEW, ABSTAIN, and BLOCKED remain non-approval states. No uncertain or protected element may be promoted to PASS. The guard prevents a false pass when a caller supplies only a boolean authorization flag.

## Affected Contracts

Only `runtime/controlled_editing_contract.py` and `tests/test_controlled_editing_contract.py` are changed, plus this evidence document. PlanModel, ConstraintMap, BIM contracts, detector logic, Golden DWG assets, workflows, and execution bridge are unchanged.

## Risk Classification

Moderate: permission decisions are security-sensitive. The fix is deliberately conservative and preserves the MVP rule that LOCKED architectural elements cannot be edited through this contract. It may reject callers that previously relied on the unsafe boolean bypass; those callers must use an explicitly editable permission state supported by the authoritative ConstraintMap and approval pipeline.

## Negative Tests

- LOCKED with `authorized=True` raises the explicit unsupported-authorization error.
- Directly constructed decisions containing LOCKED permissions still report a blocking conflict.
- Existing locked, editable, conditional, uncertainty, and impact contract tests remain passing.
- End-to-end approval bridge tests continue to reject protected or non-editable targets.

## Unresolved Findings

This PR closes the boolean bypass at the controlled-editing contract boundary. A separate review is still needed if future product requirements introduce an authorized exception process for protected elements; that process must define a typed approval record bound to project, proposal, source version, exact targets, approver identity, and evidence. No such exception is introduced here.

## Final Decision

BLOCKED pending successful exact-head PR CI Gate, Runtime Tests, Mandatory Bug Hunt, and review. No approval, merge, or auto-merge is performed.
