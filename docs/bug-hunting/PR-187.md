## Scope

WS-01: prevent rejected or invalid project-version statuses from becoming the active workspace version. Rejected versions remain recorded in history but do not replace the active version.

## Bug Hunt

Source inspection found that `ProjectWorkspaceAdapter.attach_plan()` appended every supplied status and unconditionally assigned `active_version_id`. A caller could attach a version with status `REJECTED` and make it active, bypassing the intended validated-version promotion boundary.

## Findings

WS-01: `attach_plan()` activated a rejected version. Unknown status values were also accepted and activated. This could make a rejected or malformed project version appear to be the current workspace version.

## Reproduction

Test-first regressions cover:
- Attaching REJECTED while a WORKING version is active must preserve the prior active version.
- Attaching REJECTED to an empty workspace must leave active_version_id unset.
- An unknown status must raise PROJECT_VERSION_STATUS_INVALID without mutating versions or active_version_id.

All three new tests failed against the pre-fix snapshot. After the fix, `tests/test_project_workspace.py` passed (7/7).

## Root Cause

The adapter treated version attachment and activation as the same operation. It did not validate the status value and did not distinguish rejected history from active working or validated versions.

## Regression

The adapter now accepts only the observed version states WORKING, VALIDATED, and REJECTED. All accepted versions are retained in the version history. Only WORKING and VALIDATED may become active during attachment; REJECTED never changes active_version_id. Invalid states fail before any workspace mutation.

## Required fail-closed states

REJECTED remains non-active. Unknown status is rejected. NEEDS_REVIEW, UNKNOWN, BLOCKED, and other unrecognized states are not promoted to PASS or active. The guard prevents a false pass by refusing invalid version states.

## Risk Classification

Moderate: workspace active-version selection affects which plan version downstream users see. The change is conservative and preserves existing WORKING and VALIDATED behavior while preventing REJECTED or invalid states from becoming active.

## Negative Tests

- Rejected version is recorded but does not replace an existing active version.
- Rejected version does not activate an empty workspace.
- Unknown status is rejected without mutating workspace state.
- Existing WORKING attachment and VALIDATED promotion tests remain passing.

## Unresolved Findings

This PR closes the rejected/invalid attachment activation issue. Broader lifecycle policy for archived, superseded, or review-pending version states remains outside scope and requires explicit contract definition before support is added. No false pass or security certification is claimed.
